# Ascent VRX / AR9311 (Gnd485)

This experimental board profile targets the Caddx Ascent VRX / Gnd485 receiver
(Artosyn Proxima AR9311, Cortex-A53). It builds Linux 6.18.36, hardware decoding,
fixed-mode HDMI, native SDIO radio support, USB networking and NAND recovery.
It does not include an integrated Kestrel ground application or UI.

**Normal installation boots from NAND and runs its root filesystem in RAM.**
U-Boot loads the kernel; its independent recovery initramfs verifies the installed
bundle, extracts userspace into tmpfs and starts the system. No host or SD card
is required for subsequent boots. System-file edits are ephemeral; use SD for
persistent files. USB RAM boot is also available for development and recovery.

## Build and inputs

The kernel, device tree and modules are built together. The kernel archive and
external driver sources are pinned and hash-checked. Start from the repository's
pinned Buildroot submodule, then supply this local radio input:

| Input | Location | SHA-256 |
| --- | --- | --- |
| Open8030 Ascent VRX 18.21.10 board profile | `vendor/open8030/ascent-vrx.c` | `1bc673f086b67f2a742233619d655d92aca6816932a57e2b674cbdbd4f6f12c5` |

Use Open8030's extraction tools and documented input provenance for the board
profile. The published `open8030-profiles` archive supplies the shared radio JSON
configuration, but not this Gnd485 profile. `OPEN8030_PRIVATE_DIR` overrides the
local profile directory. Never commit this input.

The `ar9311-firmware` Buildroot package downloads Caddx's official
[Ascent VRX 17.5.15 image](https://github.com/CaddxFPV-Tech/Caddx-Ascent-Firmware-Release/releases/tag/V17.5.15),
verifies its SHA-256, extracts `usr/bin/chagall.bin` from the `userapp0` UBI/SquashFS
partition, and checks the extracted binary before installing it. This runs as
part of the package build, not a general pre-build script. Host Python, LZO and
SquashFS tools are Buildroot dependencies; no system Python modules are needed.

The board selects `BR2_PACKAGE_AR9311_FIRMWARE_ASCENT_17_5_15`. Its shared source
profile specifies the download and extraction layout, and can be reused by
other boards once compatibility is validated. The blob's SHA-256 is
`99bc74cdf1e7ded785c2b65440c983f4e128727eb2bbdf309b14ddde668fd8ac`, identical to
the previously validated 17.5.8 blob. This changes how it is obtained, not the
decoder firmware installed in fpvOS.

Buildroot caches the original image under
`$(BR2_DL_DIR)/ar9311-firmware/Ascent_G_Gnd_17_5_15.img`. For an offline build,
populate that cache with the exact pinned image (or run
`make -C output/ascent-vrx ar9311-firmware-source` while online). A download
mirror can be supplied through `AR9311_FIRMWARE_SITE`; hash checks still apply.
The former `AR9311_FIRMWARE_SOURCE_DIR` raw-blob input is no longer used.
The package is proprietary/non-redistributable; extraction does not establish
permission to distribute images containing it.

The extractor's format-rejection tests use synthetic inputs and need no vendor
firmware or hardware:

```sh
python3 -m unittest discover -s br-external/package/ar9311-firmware/tests -v
```

Build the board image:

```sh
./build.sh ascent-vrx config
./build.sh ascent-vrx
```

Build outputs live in `output/ascent-vrx/images/`:

| File | Purpose |
| --- | --- |
| `Image` | Uncompressed ARM64 kernel |
| `kernel.img` | LZ4 kernel with uImage/Artosyn headers, load address `0x20200000` |
| `ascent-gnd485.dtb` | Board device tree |
| `rootfs.cpio.uboot` | Full rootfs with U-Boot ramdisk header; `.cpio.gz` also available |
| `fpvos-ascent-vrx.fwu` | Kernel, DTB and rootfs update bundle |
| `fpvos-update-ascent-vrx` | Unified static updater with embedded stock-bootstrap tools |

### Shared platform and board configuration

`ascentvrx_defconfig` selects this board through `./build.sh ascent-vrx`.

| Source | Responsibility |
| --- | --- |
| `br-external/board/common/ar9311/` | SoC device-tree include, base kernel configuration, BusyBox fragment, kernel hashes and USB/codec/MMC-clock/QSPI/display patches |
| `br-external/board/ascent-vrx/` | Memory reservations, peripheral wiring, GPIO/regulator assignments, HDMI setup, NAND partitions, rootfs overlay and image packaging |
| `br-external/package/fpvos-update/src/` | Shared USB protocol, verification and command dispatch |
| `br-external/package/fpvos-update/backends/ascent-vrx/` | Gnd485 image policy, NAND geometry, stock-runtime checks and bootstrap preparation |
| `br-external/package/fpvos-recovery/` | Gnd485 recovery initramfs and boot policy |

The shared `ar9311.dtsi` leaves peripheral controllers disabled. A new board
must provide its own memory map, firmware handoff, wiring and enabled devices.
The shared `artosyn,ar9311-gpio` controller preserves boot-time pin directions
using hardware readback; GPIO assignments and initial levels remain board policy.
The bank-aware NAND parser remains board-specific. VO/DSI and LT9611 drivers
are shared. Boards enable `artosyn,ar9311-vo` and `artosyn,ar9311-dsi`, provide
the output graph, and select `artosyn,display-profile = "ascent-1080p60"` on
both controllers for the currently supported fixed output path. Missing or
unknown profiles are rejected before hardware setup. The profile preserves
Ascent's validated raster/PHY settings; it does not imply arbitrary-mode or
other-board support. LT9611 uses `lontium,lt9611` with explicit bridge quirks.
Kernel patch directories, configuration fragments and DTS directories are applied
common-first, then board.

Host updater tools select this board with `--board ascent-vrx`.
The `ascent-gnd485.dtb` bundle component, board compatible and stock model
checks retain the hardware name for compatibility; source and output directories
use the product name `ascent-vrx`.
After updating an existing checkout, reapply the defconfig and rebuild the kernel
from a clean source directory so the relocated patch sets are applied. The
recovery build target is now `fpvos-recovery`.

To omit locally supplied codec firmware, disable `BR2_PACKAGE_AR9311_FIRMWARE`
in `make -C output/ascent-vrx menuconfig`, then use `make -C output/ascent-vrx` directly:
the wrapper reapplies the default configuration. Missing firmware leaves the
decoder disabled; SSH and storage still work. Removing installed packages requires
a clean output directory because Buildroot does not remove their old files.

For kernel configuration edits, use `./build.sh ascent-vrx kernel`, then regenerate
images with `./build.sh ascent-vrx`. For kernel patch edits, run
`make -C output/ascent-vrx linux-dirclean` before rebuilding. For updater changes,
rebuild in dependency order so the kernel includes the new recovery tools:

```sh
make -C output/ascent-vrx fpvos-update-rebuild
make -C output/ascent-vrx fpvos-recovery-rebuild
make -C output/ascent-vrx linux-rebuild
make -C output/ascent-vrx
```

## USB RAM boot and SSH

This hardware-tested path requires an unlocked existing U-Boot console and
Python 3/PyUSB on the host. Preserve the vendor boot chain and use temporary
variables only; do not `saveenv` these settings:

```text
setenv bootargs console=ttyS0,1152000 earlycon loglevel=7 mem=256M rdinit=/init
setenv fdt_high 0xffffffffffffffff
setenv initrd_high 0xffffffffffffffff
setenv kernel_comp_addr 0x24400000
setenv kernel_comp_size 0x800000
artosyn_hid_upgrade 0
```

The explicit memory limit prevents U-Boot's full-memory fixup exposing the codec
region to Linux. Keeping the initrd in place avoids relocation outside that RAM.
With the receiver's native USB cable connected, transfer all three artifacts:

```sh
mkdir -p .local/ar9311-boot
sudo python3 scripts/ar9311-ram-transfer.py write-verify 0x24400000 \
  output/ascent-vrx/images/kernel.img --report .local/ar9311-boot/kernel.json
sudo python3 scripts/ar9311-ram-transfer.py write-verify 0x22080000 \
  output/ascent-vrx/images/ascent-gnd485.dtb --report .local/ar9311-boot/dtb.json
sudo python3 scripts/ar9311-ram-transfer.py write-verify 0x26000000 \
  output/ascent-vrx/images/rootfs.cpio.uboot --report .local/ar9311-boot/initrd.json
```

The tool restricts transfers to these RAM windows and verifies by readback; it
has no flash command. Use new report paths on subsequent runs. After all transfers
succeed, send Ctrl-C through UART to leave the loader, then run:

```text
bootm 0x24400000 0x26000000 0x22080000
```

UART is **1.8 V, 1152000 baud, 8N1**. The development console opens a root shell
on Enter. Native USB exposes ECM networking and the updater's CDC ACM interface.
SSH is **root:root** at `192.168.3.102/24`; host keys are generated in RAM each
boot. Configure the host side as `192.168.3.100/24`, using NetworkManager or:

```sh
ip -br link
sudo ip address replace 192.168.3.100/24 dev enx029311000002
sudo ip link set enx029311000002 up
ssh root@192.168.3.102
scp -O clip.hevc root@192.168.3.102:/tmp/
```

Substitute the actual interface name and avoid conflicting routes. Dropbear
includes SCP, not SFTP. Stable gadget MACs are `02:93:11:00:00:01` (device) and
`02:93:11:00:00:02` (host); these defaults target one receiver per host.

## SD, decoding, display and radio

### Front-panel input and beeper providers

The Gnd485 board enables I²C3 (`0x01206000`) and built-in `i2c-dev`, exposing
`/dev/i2c-3`. Stock firmware reads its external button ADC at 7-bit address
`0x54`: write register pointer `0x00`, then repeated-start read two bytes.
The big-endian reply is converted with `((word >> 4) & 255) * 3300 / 256`
millivolts. Stock nominal key centres are REC 400, UP 800, LEFT 1000, RIGHT 1200,
OK 1400, DOWN 1600 and ESC 1800 mV, with a ±89 mV matching window. LINK is
separate: GPIO bank A offset 2, active-low, available through the existing GPIO
character interface. Find the bank by its `ar-gpio0` label rather than a fixed
`/dev/gpiochipN` index. These mappings come from the Gnd485 branch of official
17.5.8 firmware; they are not the VRX Pro's SoC ADC mapping.

`CONFIG_PWM_ARTOSYN` supplies the eight-channel PWM controller at `0x01000000`.
The beeper uses channel 0. Discover the PWM class entry through its `device`
link to `1000000.pwm`, rather than assuming `pwmchip0`. Stock uses a 1,000,000 ns
period (1 kHz), with duty controlling drive level. The provider supports normal
polarity only, rejects unrepresentable periods, disables the affected channel
before updating its separate high/low counters, and disables it on release.
It does not claim a channel or emit a startup tone. The second PWM controller,
used by a different AR9311 goggle's buzzer, remains absent from this board.

Kestrel owns ADC decoding/debounce, LINK actions and asynchronous beep patterns.
No stock key daemon, evdev key translation or `pwm-beeper` consumer is started
by this board profile. The updater and Kestrel must hand off PWM ownership if
upgrade notifications need to continue after Kestrel exits. Pinmux and these
peripheral gates still rely on boot firmware, as the existing I²C1 interface
does; this change does not establish general pinctrl/clock ownership.

The provider image was installed through the native USB updater with programming
readback and exact boot-bundle verification, then tested after a full power cycle.
I²C3 transactions succeeded with the ADC idle at zero, and LINK read high.
PWM rejected inverse polarity, a 30-second period beyond its supported counter
range, and a one-nanosecond period below one clock cycle. After bounded 1 kHz,
10% duty pulses, release/reacquisition and debugfs hardware readback both showed
the channel disabled with the expected counter-derived period/duty. Other PWM
channels remained unconfigured.

A subsequent physical test confirmed all seven menu keys: UP 786, DOWN
1585–1598, LEFT 992, RIGHT 1185–1198, OK 1392, ESC 1778 and REC 386 mV,
all within the stock windows without an offset. Each returned to zero after
release. LINK changed high → low → high independently of the ADC. One brief
464 mV sample during LEFT release landed in the REC window, demonstrating why
Kestrel must debounce transitions. Two 100 ms, 1 kHz, 10% duty pulses, separated
by 250 ms, were requested, and PWM was disabled afterward. Audible output remains
unverified; the operator corrected the earlier hearing-confirmation claim.
Button transitions and PWM register behavior are validated. Beeper acoustic
validation and Kestrel menu/action integration remain.

The platform check reported zero failures on both boots. Eight HEVC 1080p frames
decoded byte-for-byte identically to the retained reference. Kestrel HDMI output
was captured after capture-device power cycling; the existing black-frame/re-lock
quirk remains. Boot-protected, stock-rootfs and vendor-data hashes were unchanged,
and NAND ECC failure counters remained zero. The separate USB RAM-boot trial was
unavailable because the existing U-Boot rejected the saved development password;
no bootloader or persistent environment modifications were made.

### SD and media

The SD service mounts an existing FAT, exFAT or ext4 filesystem at `/mnt/sd` and
creates `/mnt/sd/fpvos`. It identifies the removable controller rather than a
fixed block-device number and never formats or repairs storage. Multiple candidate
filesystems require manual selection. A missing card does not prevent boot.
Close files and run `/etc/init.d/S45ar9311-sd stop` before removing the card;
`start` mounts it again. Ext4 is suitable for persistent development files.

`ar9311-media-start` loads Wave5 using the hash-checked bundled microcode. If it
was omitted at build time, the helper can use a matching copy at
`/mnt/sd/fpvos/firmware/chagall.bin`. The interface is V4L2 stateful decoding,
normally `/dev/video0`. Internal codec buffers use `0x30000000–0x3fffffff`;
the secure `0x23400000–0x23ffffff` reservation remains excluded from Linux.

Use `ar9311-decode-test` for short Annex-B H.264/HEVC streams, at most 1 MiB:

```sh
ar9311-decode-test /dev/video0 hevc /tmp/clip.hevc /tmp/decoded.yuv 8
```

Supply the actual frame count; output must not already exist. It writes visible
I420 pixels without stride padding. Compare with host software decoding to verify
pixels independently of HDMI. The observed firmware may report `0x800` during
OUTPUT STREAMOFF after draining; this does not excuse incorrect output or an
error during active decoding.

`ar9311-play` validates decoding and display together:

```sh
ar9311-play hevc /mnt/sd/fpvos/clip.hevc --frames 360 --fps 60 --hold 3
```

The current display mode is **1920×1080, 8-bit I420, BT.709 limited range**;
no scaling, crop, container demuxing or audio is provided. Stop other DRM clients.
The tool shares DRM CMA buffers with V4L2 via DMA-BUF, waits for page flips and
retains buffers until safe to recycle. No decoded-pixel CPU copy is required.
It presents completed frames, not unfinished slices, and stops display on exit.
No test player runs automatically at boot. `--force` permits fixed scanout when
hotplug/EDID is unavailable; a successful forced run does not prove visible output.

The bridge marking is LT9511 / C1311133B; the observed register ID and tested
behavior use the shared LT9611 driver with board-selected quirks. Control is on I2C1,
address `0x3b`, reset GPIO107. The board enables `lontium,page-select-quirk`
for reliable register-bank selection and `lontium,fixed-1080p60-quirk` for its
calibration sequence. These are independent opt-ins; the latter restricts output
to RGB CEA-16 at 148.5 MHz with DSI sync-event input, without DVI or audio.
Do not write bridge registers while DRM owns it.
Hotplug/EDID and display compatibility remain limited; validate moving output
on a direct display as well as capture devices, which can repeat stale frames.

The radio package depends on `BR2_FPVOS_SOC_AR9311`; another AR9311 board can
select it without selecting Ascent wiring or storage policy. The board chooses
the Open8030 profile, ground/station role and **native SDIO** transport.
Ascent uses its private `vendor/open8030/ascent-vrx.c` profile and the published
`bb_config_gnd_open8030.json` configuration. The host loads the stable installed
names `open8030.img` and `open8030.json`. Startup uploads firmware into radio
RAM and creates `/dev/arlink0`. Initialize it with `ar9311-radio -t 10`; for a paired air unit:

```sh
ar9311-radio -p XX:XX:XX:XX -s -t 20 -r -o /mnt/sd/fpvos/radio-capture.raw
```

`-s` sends the air-start handshake requesting 1080p60/25 mW and checks ten ACKs;
without it, no camera commands are sent. Receiver uplink is also fixed at 25 mW.
`-r` requires received bytes; the capture is framed radio data, not Annex-B video.
These checks do not prove uninterrupted or decodable reception. Only one client
may run; closing it stops the radio. Recover failed SDIO startup with a cold boot,
not repeated module resets while the MMC host is active. Pairing, reconnect and
radio-to-display orchestration belong to the future ground application.

## Platform checks and known limits

```sh
ar9311-platform-check
ar9311-platform-check --storage --memory
ar9311-pstore-save
```

The checker covers CPUs, mounts, watchdog registration, pstore, USB setup,
MMC clocks and driver readiness. Optional checks write/fsync/reread a temporary
8 MiB SD file and run a 16 MiB memtester pass. They do not validate RF or pixels.
The pstore helper explicitly archives crash records to a new SD directory without
erasing the originals. Ramoops reserves 1 MiB at `0x2ff00000`; records survive
warm recovery but may be lost after power removal or another OS reuses that RAM.

Vendor SPL/U-Boot/secure firmware still initialize DDR, PSCI and parts of pinmux,
clocks and PHYs. Linux owns the SD/SDIO source clocks and gates; SD stays at 3.3 V,
up to 50 MHz. General pinctrl/reset ownership, GPIO interrupts, RTC ticking and
thermal monitoring are incomplete. The inherited watchdog can restart the board
but cannot currently be disarmed; halt/poweroff may therefore end in a reset.
A panic requests restart after five seconds. HDMI audio, broad mode/hotplug
support, and robust live-stream recovery are not implemented or fully validated.

## NAND installation and vendor restoration

Installation is explicit and writes internal NAND. This board path is an
exception to the project's SD-only policy and requires upstream review.
The installer protects the existing boot chain and stock rootfs:

| Offset | Size | Region | Access |
| --- | --- | --- | --- |
| `0x0000000` | `0xb40000` | Boot chain, GPT, environment, factory | Read only |
| `0x0b40000` | `0x600000` | Shared kernel, including recovery | Read/write |
| `0x1140000` | `0x060000` | Shared DTB | Read/write |
| `0x11a0000` | `0x1500000` | `userapp0`: stock or fpvOS | Active stock read-only; inactive read/write |
| `0x26a0000` | `0x1500000` | `userapp1`: stock or fpvOS | Active stock read-only; inactive read/write |
| `0x3ba0000` | `0x4460000` | Remaining vendor data | Read only |

Preflight requires the observed layout, geometry and exactly one stock bank
selected by GPT. Only the other bank is used for fpvOS; neither bank is assumed
to be inactive. The kernel and updater share the same GPT decoder: the kernel
registers the active bank as read-only `vendor-rootfs` and the inactive bank as
`fpvos`. Invalid metadata leaves NAND read-only. Valid redundant GPT records
are supported, but GPT and its selection are never written. Damaged/ambiguous
records and attached UBI on writable regions are refused. Installation checks
every erase range for bad blocks before any write; it does not skip/remap them.
Boot checks only GPT, control records and the stored images, so unused bad tail
blocks do not prevent an otherwise intact system from booting.
Recovery readiness validates the layout and storage ownership without requiring
healthy update targets. Bad blocks in the fpvOS bank, including its control and
header blocks, do not block vendor kernel/DTB restoration. Each operation still
checks the blocks it uses; an install refuses bad erase ranges before any write.

The updater takes a private RAM copy of the uploaded package, verifies that copy
once inside the NAND transaction, and uses it for programming and readback. It
keeps affected regions in RAM for attempted restoration after write failures.
Uploads are capped at the board profile limit before staging begins.
The first two eraseblocks of the inactive bank hold redundant clean-mode records.

**Shared kernel/DTB writes are not power-loss atomic.** This is not whole-system
A/B or boot-health rollback. Keep original host backups and the U-Boot USB RAM
recovery path available. An invalid root bundle leaves recovery running; damage
to the kernel/DTB may require reloading them from the host. If restoration fails,
keep power on to preserve RAM backups. There is no bad-block remapping.

For first installation, use the tested USB RAM boot above. Subsequent updates
start from the NAND-installed system:

```sh
PORT=/dev/serial/by-id/usb-fpvOS_AR9311_development_network_fpvos-ar9311-if02
python3 tools/fpvos-update/client.py --board ascent-vrx --port "$PORT" info
python3 tools/fpvos-update/client.py --board ascent-vrx --port "$PORT" install \
  output/ascent-vrx/images/fpvos-ascent-vrx.fwu
```

The host requests clean mode, reconnects after the recovery reboot, uploads and
installs, then reboots and verifies the reported bundle hash. In a RAM-loaded
system, clean mode instead quiesces clients and unmounts persistent storage.
A disconnect does not cancel a flash transaction. `--no-reboot` leaves the device
in recovery. `verify` checks a bundle without programming: its 90%/state2 result
is not installation success; state4/100% means installation was readback-verified.
Interrupted uploads restart from the beginning. Failed restoration blocks further
service updates/reboots so evidence and backups remain accessible via SSH/UART.

The transport follows vendor OTRA CDC framing, but `.fwu` is an fpvOS format.
It checks board identity, lengths and integrity, not signatures or version order.
Do not submit it to the stock flash engine; vendor desktop-tool compatibility
is not established. To return to stock, package complete original partition
backups named `kernel.before.bin` and `dtb.before.bin`:

```sh
python3 tools/fpvos-update/package.py --board ascent-vrx --vendor-restore \
  /path/to/original-backups /path/to/vendor-restore.fwu
python3 tools/fpvos-update/client.py --board ascent-vrx --port "$PORT" install \
  /path/to/vendor-restore.fwu
```

This restores the shared kernel/DTB byte-for-byte. Both rootfs banks, including
the inactive bank's control area, are preserved by the restore transaction.
It does not accept arbitrary vendor `.img` packages. Stock uses a different USB
identity, so verify its boot separately. Returning to fpvOS uses U-Boot USB RAM
recovery again, or the experimental stock clean-hook path below.

## Built-in stock clean-hook preparation

`fpvos-update bootstrap` embeds BusyBox and preparation helpers in the same static
updater used by fpvOS and recovery. The separate 14-line launcher is necessary
because stock's `web:path` hook **sources a shell script**, not an executable.
There is no separate bootstrap binary or payload archive.

This path is experimental. The development branch was hardware-tested from stock
18.21.10 with either stock bank selected, including a browser round trip back to
stock. The updater review fixes were subsequently hardware-tested on Gnd485
with stock bank 0 selected: stock clean-hook preparation, NAND installation,
fpvOS self-update, PSU cold boot, and restoration to stock 18.21.10 all passed.
Vendor restoration was tested from both stock preparation and native recovery;
both rootfs banks, including their control areas, were preserved. Native recovery
readback confirmed that only the shared kernel/DTB changed, matching the original
vendor bytes. Oversized uploads and a corrupt package were rejected, the platform
check reported zero failures, and all MTD ECC failure counters were zero.

This regression run used a Python USB protocol client, not the browser UI, and
an incremental build. It did not inject power loss during writes, physical bad
blocks, or concurrent staged-file mutations; the latter two retain host-test
coverage. Browser integration must verify and stage `fpvos-update-ascent-vrx` as `/usrdata/fpvos-update` and the launcher
as `/usrdata/fpvos-bootstrap.sh`, without vendor FileEnd, then arm the consumed
one-shot `web:/usrdata/fpvos-bootstrap.sh` selector and request a normal reboot.
Do not run the launcher as a general startup script.

The updater validates the supported stock Linux4.9.38 runtime, moves itself into
private tmpfs, removes staged copies, extracts only its compiled-in tools and
performs storage/USB preparation. The receiver performs clean readiness once
before serving requests. If it fails, the receiver remains available for USB
info/status queries and a clean retry, but refuses uploads until readiness
succeeds. Stock mount checks use PID 1's view outside the chroot; missing host
mount information fails the check. It starts
our receiver rather than the vendor flash engine. Stock access uses the `kernel` and
`dtb` nodes and the inactive `userapp0` or `userapp1` node; the master NAND node
is opened read-only for GPT access. Installation still requires a
separate validated `.fwu` upload. It does not export host backups.

## Updater source and tests

`br-external/package/fpvos-update` owns shared transport, verification and multicall
dispatch; `backends/ascent-vrx` owns image/NAND policy and clean-mode helpers. The
host and C code share `profile.json`. `fpvos-recovery` builds the independent
initramfs; it does not include the final system's modules or require SD.
The executable supports `receive`, `verify`, `nand` and `bootstrap`; compatibility
symlinks keep startup/recovery entry names working. The backend helper publishes
atomic status updates and returns 10 when clean mode requires a reboot.

```sh
python3 -m unittest discover -s tools/fpvos-update/tests -v
```
